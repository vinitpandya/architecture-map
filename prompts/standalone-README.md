# Mapping your own estate

Two prompts, the two schemas they produce against, and a worked example of each.
Everything here is self-contained: hand a prompt to Claude inside one of your
repositories and it will produce the JSON this app ingests. Nothing needs to be
running first.

> Generated by `npm run prompts` from `prompts/` and `schema/`. Do not edit the
> files here — edit the template or the schema and rebuild.

## The order to do it in

**1 · Scan each repository, one at a time.**
[`1-scan-a-repository.md`](1-scan-a-repository.md)

Run it from a checkout of the repo, with Claude Code or by pasting the prompt
into a session that can read the tree. It produces one manifest per deployable
service: what the service owns, what it talks to, and a file and a line behind
every claim.

One repository at a time, deliberately. A scan sees one repo and nothing else,
which is what makes the ids reproducible — two people scanning two repos in
separate sessions must produce the byte-identical string for the same topic, or
the estate comes out as a set of islands. The schema's `nodeId` description is
the rule that makes that work; it is the part to read twice.

**2 · Load them.** Drop the files in `inbox/` and press **Sweep inbox** on the
Scan page, or `POST /api/ingest`. Check one first with
`npm run validate -- <file>.json` — it names the offending field and its path,
and it routes on the document's shape, so it works for either kind.

Once the manifests are in, most of the app lights up: the map, search, drift,
the estate lists. That is Layer A, and it is derived entirely from code.

**3 · Write down what the business does.**
[`2-author-a-process-pack.md`](2-author-a-process-pack.md)

This one is not a scan. Nobody can derive it from a codebase, because the
knowledge is not in the codebase — it comes out of a Confluence page, a diagram,
a runbook, or an hour with the person who knows. Run it with that material as
input.

Do this **after** step 2, and prefer the version the app renders for you: the
Scan page's *Processes* tab fills the same prompt with every component id in
your map, which is the thing that stops a pack referencing things that do not
exist. The copy here is for when you have not got that far yet.

**4 · Say who owns what.** Copy `teams.example.json` to `teams.json` at the repo
root and list your teams and departments. Optional — the map works without it —
but it is what turns "which teams does this process cross" from approximate into
exact, and it is what catches `Trading` and `trading` being filed as two teams.

## What you get for each step

| After | The app can answer |
|---|---|
| one repo scanned | what this service owns, talks to, and cites |
| the estate scanned | which processes break if this topic stops; who else writes this database; where two services disagree about a contract version |
| a process pack loaded | which components "Getting estimate" actually touches, across every repo — and where the document and the code disagree |
| `teams.json` | which teams a process crosses, and where one team's work ends and another's begins |

## The three rules that matter most

These are in the prompts too, but they are the ones worth knowing before you
start, because getting them wrong is expensive to undo.

**Never invent an identifier.** If a topic name is assembled at runtime, or a
base URL comes from an environment variable with no default in the repo, it goes
in `unresolved` with the literal expression. An honest gap is useful. A
plausible invention is worse than useless: it is indistinguishable from a real
finding, and it silently poisons every view built on top of it.

**Ids are the contract between sessions.** Everything else in a manifest is
descriptive and can be corrected later. An id that does not match what another
repo's scan produced makes two nodes where there should be one, and no amount of
later editing finds them all. Follow the `nodeId` rules exactly.

**A process pack never creates a component.** It references what a scan already
found. A reference that does not resolve is reported as a finding — and that
finding is the point of the whole exercise, because it means either the scan
missed something or the document has gone stale. Substituting a component that
does exist, because it looked close enough, destroys exactly the signal you are
here for.

## Codes, briefly

A process is identified by its code: `2`, `2.1`, `2.1.1`, written `L2` and so
on. The code carries the hierarchy — the number of segments is the level, the
parent is the code minus its last segment — and it carries the order, so `2.1`
happens before `2.2`.

The levels are **decomposition, not sequence**: each one says the same thing in
more detail, and a level 3 is already the atomic unit of work. There is no step
list underneath it. This is the single thing people get wrong, and the prompt
spends its first section on it.

Codes are permanent. People cite them in tickets, so renumbering has a real
cost. Pick a level 1 number nobody has taken and keep it.
